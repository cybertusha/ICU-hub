# 1. EXECUTIVE SUMMARY

## 1.1 Product Overview

The Real-Time IoT-Based ICU Patient Monitoring System is an intelligent patient monitoring solution designed to continuously collect, process, transmit, visualize, and monitor patient vital signs using Internet of Things (IoT) technology and cloud computing.

The system connects a bedside patient monitoring environment with a Raspberry Pi-based IoT gateway and AWS Cloud infrastructure. A centralized Doctor Web Application allows authorized medical personnel to monitor patient conditions remotely through real-time dashboards, historical graphs, and automated alerts.

The project will initially operate in Demonstration Mode, where a computer simulates an ICU patient monitor and generates realistic patient vital readings. Raspberry Pi receives these readings, processes them, and securely transmits them to AWS Cloud.

AWS processes and stores incoming patient data. The Doctor Dashboard receives real-time updates and generates alerts whenever configured monitoring thresholds are crossed.

The architecture will also support future integration with actual medical sensors, allowing the demonstration prototype to evolve into a hardware-integrated monitoring system.

## 1.2 Core Product Concept

The system consists of five major components:

1. **Bedside Patient Monitor:** A PC-based interface that simulates an ICU monitoring device and generates patient vital readings.
2. **Raspberry Pi IoT Gateway:** Collects, validates, preprocesses, and securely transmits patient data.
3. **AWS Cloud Infrastructure:** Processes incoming data, manages patient records, stores historical readings, and handles alerts.
4. **Doctor Web Application:** Provides centralized patient monitoring, visualization, alert management, and historical analysis.
5. **Real-Time Communication System:** Ensures automatic synchronization between the patient monitor, Raspberry Pi, AWS, and Doctor Dashboard.

## 1.3 Product Vision

To demonstrate an intelligent, reliable, and cloud-connected ICU patient monitoring ecosystem that enables continuous patient vital monitoring, centralized data access, automated abnormality detection, and timely notification through IoT and cloud technologies.

# 2. PROBLEM STATEMENT

Traditional patient monitoring environments often depend on bedside monitoring equipment and require healthcare professionals to be physically present to observe patient conditions.

Monitoring multiple patients simultaneously can become challenging, especially when patient information is distributed across different monitoring devices.

Additionally, manually observing vital signs may delay the identification of abnormal conditions, and conventional monitoring setups may not provide centralized historical patient information or remote access.

There is a need for an integrated monitoring solution that can:

- Continuously collect patient vital signs.
- Transmit patient information to a centralized platform.
- Allow doctors to monitor patients remotely.
- Automatically identify abnormal vital readings.
- Generate timely alerts when configured thresholds are crossed.
- Maintain patient monitoring records.
- Support reliable communication during temporary internet interruptions.

The proposed system addresses these challenges through an IoT-based monitoring gateway, AWS Cloud infrastructure, and a centralized Doctor Web Application.

**Note:** The prototype demonstrates these capabilities using simulated patient data. It is not intended for clinical diagnosis or treatment.

# 6. HIGH-LEVEL SYSTEM ARCHITECTURE

## 6.1 Architecture Overview

The system follows an IoT-to-Cloud architecture.

**Complete Data Flow:**

Dummy ICU Environment → Raspberry Pi → AWS IoT Core → AWS IoT Rules → AWS Lambda → Amazon DynamoDB → Real-Time Communication → Doctor Dashboard.

**Platform:** PC / Web Application

The PC acts as a simulated bedside patient monitoring device.

It continuously generates realistic-looking patient vital readings.

The interface displays:

- SpO2 (%)
- Body Temperature (°C)
- Respiratory Rate (breaths/min)
- ECG Waveform
- Patient ID
- Patient Name

- Current Timestamp

**Functional Requirements:**

- FR-001: The system shall generate continuously updating simulated vital readings.
- FR-002: The system shall display patient readings in real time.
- FR-003: The system shall provide selectable patient simulation scenarios.
- FR-004: The system shall support starting and stopping the simulator.
- FR-005: The system shall transmit readings to Raspberry Pi through a local network interface.
- FR-006: The system shall clearly identify simulated data.
- FR-007: The system shall display communication status.

### Supported Simulation Scenarios

**1. Normal Patient**
- Heart rate within the configured normal demonstration range.
- Normal SpO2.
- Normal temperature.
- Normal respiratory rate.
- Stable ECG visualization.

**2. High Heart Rate**
- Heart rate increases above the configured threshold.
- Heart rate trend updates.
- Appropriate warning or critical alert is generated according to configured rules.

**3. Low SpO2**
- Oxygen saturation decreases.
- Patient status changes according to configured thresholds.
- Appropriate alert is generated.

**4. High Temperature**
- Body temperature increases.
- Temperature trend updates.
- Alert is generated when the configured threshold is crossed.

**5. Abnormal Respiratory Rate**
- Respiratory rate moves outside the configured demonstration range.
- The system detects the abnormal reading.
- The dashboard receives an appropriate alert.

**6. Critical Patient Condition**
- Multiple vital parameters may enter configured critical ranges.
- Patient monitoring status changes to critical.
- Multiple relevant alerts can be generated.

**7. Recovery Scenario**
- Patient readings return to configured acceptable ranges.
- The monitoring system detects recovery.
- Existing alert history is retained.

### Component 2: Raspberry Pi IoT Gateway

**Platform:** Raspberry Pi  
**Programming Language:** Python  
**Communication Protocol:** MQTT over TLS

Raspberry Pi acts as the intermediary between the bedside patient monitoring environment and AWS Cloud.

It is responsible for receiving, processing, validating, buffering, and securely transmitting patient monitoring data.

#### Functional Requirements

- FR-009: Raspberry Pi shall receive patient readings from the PC through a local network API or MQTT.
- FR-010: The gateway shall validate incoming patient data.
- FR-011: The gateway shall filter invalid or malformed readings.
- FR-012: The gateway shall attach timestamps and device identifiers.
- FR-013: The gateway shall preprocess incoming data.
- FR-014: The gateway shall publish structured JSON messages to AWS IoT Core.
- FR-015: The gateway shall monitor its cloud connection.
- FR-016: The gateway shall automatically reconnect after connectivity restoration.
- FR-017: The gateway shall log communication errors.
- FR-018: The gateway shall support offline data buffering.
- FR-019: The gateway shall synchronize buffered readings when internet connectivity returns.
- FR-020: The gateway shall support future sensor integration.

#### Operating Modes

**Mode 1: Simulation Mode**

- Receive simulated readings from the PC.
- Validate incoming readings.
- Process the data.
- Publish readings to AWS IoT Core.

**Mode 2: Hardware Mode**

- Read data from connected sensors through suitable hardware interfaces.
- Validate sensor measurements.
- Process incoming data.
- Publish measurements to AWS IoT Core.

The sensor layer must be modular so additional sensors can be integrated without redesigning the entire application.

#### Recommended Python Modules

- `main.py` – Main gateway execution.
- `sensor_manager.py` – Sensor communication.
- `data_processor.py` – Data validation and preprocessing.
- `mqtt_client.py` – AWS IoT MQTT communication.

- `offline_queue.py` – Local data buffering and synchronization.
- `connectivity_manager.py` – Internet and cloud connection monitoring.
- `config.py` – Configuration management.

### Component 3: AWS Cloud Infrastructure

**Cloud Provider:** Amazon Web Services

AWS will provide the cloud infrastructure required for receiving, processing, storing, and distributing patient monitoring information.

#### A. AWS IoT Core

Purpose: Secure communication between Raspberry Pi and AWS Cloud.

Requirements:

- Register Raspberry Pi as an AWS IoT Thing.
- Generate and configure device certificates.
- Establish secure MQTT communication.
- Configure IoT policies.
- Create device-specific MQTT topics.
- Authenticate incoming messages.
- Monitor device connectivity.

Suggested MQTT Topics:

`icu/devices/{deviceId}/vitals`

`icu/devices/{deviceId}/status`

`icu/patients/{patientId}/alerts`

`icu/devices/{deviceId}/commands`

#### B. AWS IoT Rules

Purpose: Route incoming MQTT messages to cloud processing services.

Requirements:

- Receive patient vital messages.
- Validate topic and message structure.
- Trigger AWS Lambda processing.
- Route device status updates.
- Handle invalid message conditions.

#### C. AWS Lambda

Purpose: Serverless processing of patient monitoring information.

Responsibilities:

- Receive incoming readings.
- Validate message fields.
- Check timestamps and message identifiers.
- Process patient vital data.
- Apply configurable threshold rules.
- Generate alert events.
- Store patient readings.
- Update patient monitoring status.
- Handle duplicate messages.
- Publish updates to the real-time communication layer.

#### D. Amazon DynamoDB

Purpose: Store patient information, monitoring readings, alerts, and device status.

**Recommended Tables:**

1. `Patients`
2. `VitalReadings`
3. `Alerts`
4. `Devices`
5. `ThresholdConfigurations`
6. `Users` (if not using a managed authentication service)

Suggested data organization:

- Patients: Partition key `patientId`.
- VitalReadings: Partition key `patientId`, sort key `timestamp`.
- Alerts: Partition key `patientId`, sort key `alertTimestamp`.
- Devices: Partition key `deviceId`.
- ThresholdConfigurations: Partition key `configurationId`.

Additional indexes should support queries by date, patient, alert status, and device.

#### E. Amazon API Gateway

Purpose: Provide secure APIs for the Doctor Web Application.

Required API operations:

- Authenticate users.
- Retrieve patients.
- Retrieve individual patient information.
- Retrieve historical readings.
- Retrieve alerts.
- Acknowledge alerts.
- Resolve alerts.
- Retrieve device status.
- Update permitted monitoring configurations.

#### F. Real-Time Communication

Use API Gateway WebSocket or another suitable secure real-time communication mechanism.

Requirements:

- Deliver new patient readings.
- Deliver newly generated alerts.
- Update device connectivity status.
- Maintain authenticated connections.
- Handle disconnected clients.
- Re-establish connections when possible.

# 8. AUTOMATED ALERT MANAGEMENT SYSTEM

## 8.1 Overview

The Alert Management System identifies abnormal patient readings based on configurable monitoring thresholds.

Alert generation must happen through validated backend processing rather than frontend-only animations.

## 8.2 Initial Demonstration Thresholds

The following values are example demonstration thresholds:

| Parameter | Example Warning Condition |
|---|---|
| Heart Rate | Below 60 or above 100 BPM |
| SpO2 | Below 94% |
| Temperature | Above 38°C |
| Respiratory Rate | Below 12 or above 20 breaths/min |

These thresholds are configurable demonstration values, not universal clinical standards.

## 8.3 Alert Severity

**INFO**
- Informational events.
- Device status updates.
- Monitoring-related notifications.

**WARNING**
- A configured warning threshold has been crossed.
- The patient requires attention according to demonstration rules.

**CRITICAL**
- A configured critical condition has been detected.
- Immediate attention is indicated within the demonstration environment.

The exact severity mapping must be configurable.

## 8.4 Alert Data Structure

Every alert shall contain:

- Alert ID.
- Patient ID.
- Parameter Name.
- Detected Value.
- Configured Threshold.
- Alert Severity.
- Timestamp.
- Alert Description.
- Acknowledgment Status.
- Resolution Status.

## 8.5 Alert Functionalities

- FR-041: The system shall automatically generate alerts when configured conditions are met.
- FR-042: Alerts shall be stored in DynamoDB.
- FR-043: Alerts shall be delivered to the dashboard in real time.
- FR-044: The system shall provide critical alert sound notifications.
- FR-045: Doctors shall be able to acknowledge alerts.
- FR-046: Doctors shall be able to resolve alerts.
- FR-047: The system shall maintain alert history.
- FR-048: Users shall be able to filter alerts by patient and severity.
- FR-049: The system shall prevent excessive duplicate alerts.
- FR-050: The system shall detect recovery conditions.
- FR-051: Resolved alerts shall remain available in historical records.

## 8.6 Duplicate Alert Prevention

Implement:

- Alert cooldown periods.
- Repeated-event detection.
- Existing active alert checks.
- Recovery detection.
- New alert generation after a configured recurrence condition.

Example:

If SpO2 remains below a configured threshold for several consecutive readings, the system should avoid generating a new notification for every incoming reading.

When the value returns to an acceptable range, the system records the recovery event and updates the alert lifecycle.

## 8.7 Alert Lifecycle

1. Reading received.
2. Reading validated.
3. Threshold evaluated.
4. Alert condition detected.
5. Alert generated.
6. Alert stored.
7. Real-time notification delivered.
8. Doctor acknowledges alert.
9. Condition recovers.
10. Doctor resolves alert.
11. Alert remains in historical records.

Acknowledgment and resolution must be separate operations.

# 10. REAL-TIME DATA COMMUNICATION

## 10.1 Data Pipeline

The complete communication process shall follow these steps:

**Step 1:** PC generates simulated patient readings.

**Step 2:** PC transfers readings to Raspberry Pi through a local network API or MQTT.

**Step 3:** Raspberry Pi validates the incoming information.

**Step 4:** Raspberry Pi adds device identifiers, timestamps, and message IDs.

**Step 5:** Raspberry Pi publishes the structured JSON message to AWS IoT Core using MQTT over TLS.

**Step 6:** AWS IoT Rules route the incoming message to AWS Lambda.

**Step 7:** AWS Lambda validates, processes, and evaluates the readings.

**Step 8:** Processed data is stored in DynamoDB.

**Step 9:** The real-time communication layer distributes updates to authenticated dashboard clients.

**Step 10:** Doctor Dashboard updates patient readings, charts, and alerts automatically.

## 10.2 Standard JSON Message Structure

All components shall use a consistent data format.

Example:

```json
{
  "messageId": "MSG-000001",
  "deviceId": "ICU-PI-001",
  "patientId": "PATIENT-001",
  "timestamp": "2026-11-16T10:30:00Z",
  "mode": "SIMULATION",
  "vitals": {
    "heartRate": 82,
    "spo2": 98,
    "temperature": 36.8,
    "respiratoryRate": 18,
    "ecg": []
  }
}
```

## 10.3 Data Validation

The system shall validate:

- Required fields.
- Data types.
- Patient identifiers.
- Device identifiers.
- Timestamp format.
- Valid numerical values.
- Message identifiers.
- Data source mode.

Invalid messages shall be rejected or quarantined and logged.

Duplicate messages shall not create duplicate historical records or alerts.

## 10.4 Real-Time Dashboard Updates

The dashboard shall not depend on manual browser refreshes.

It shall receive:

- New patient readings.
- Updated patient status.
- New alerts.
- Alert status changes.
- Device connection updates.

The system shall handle temporary disconnections and re-establish communication when possible.

# 11. OFFLINE-FIRST RELIABILITY

## 11.1 Overview

Offline-first reliability is a key architectural requirement.

The system must continue local monitoring and data logging even when the internet connection is temporarily unavailable.

The Raspberry Pi will maintain a local buffer for readings that cannot be transmitted to AWS.

## 11.2 Offline Operation

When internet connectivity is lost:

1. The PC simulator continues generating patient readings.
2. Raspberry Pi continues receiving local data.
3. Local validation and preprocessing continue.
4. Patient readings are stored in a persistent local queue.
5. Local logging continues.
6. Local monitoring interfaces continue functioning.
7. Cloud connection status changes to offline.
8. AWS transmission is temporarily suspended.

## 11.3 Automatic Recovery

When internet connectivity is restored:

1. Raspberry Pi detects network availability.
2. MQTT connection is re-established.
3. Device authentication is performed.
4. Buffered messages are retrieved.
5. Pending messages are published to AWS.
6. Successfully transmitted messages are marked as synchronized.
7. The Doctor Dashboard receives new cloud updates.
8. Device status returns to connected.

## 11.4 Reliability Requirements

- FR-058: Local patient data collection shall continue during internet interruptions.
- FR-059: Raspberry Pi shall persistently buffer unsent readings.
- FR-060: The gateway shall automatically attempt reconnection.
- FR-061: Buffered readings shall synchronize after reconnection.
- FR-062: Duplicate message processing shall be prevented.
- FR-063: Synchronization failures shall be logged.
- FR-064: The system shall display device connectivity status.

**Important:** Offline-first operation guarantees local continuity only within the available local hardware and storage capabilities. Remote dashboard updates are unavailable while cloud connectivity is interrupted unless a separate local dashboard connection is implemented.

# 23. RISKS AND MITIGATION STRATEGY

| Potential Risk | Mitigation |
|---|---|
| Internet disconnection | Local persistent buffering and automatic reconnection |
| Raspberry Pi connection failure | Connectivity monitoring and retry logic |
| Invalid patient readings | Input validation and rejection |
| Duplicate MQTT messages | Unique message IDs and idempotent processing |
| Excessive alerts | Cooldown and repeated-event handling |
| AWS configuration errors | Deployment documentation and configuration validation |
| Dashboard disconnection | WebSocket reconnection and data refresh |
| Data loss during power failure | Persistent local storage and controlled synchronization |
| Incorrect patient-device mapping | Explicit device-patient assignment validation |
| Hardware integration difficulty | Modular sensor abstraction layer |

# 26. FINAL PRODUCT VISION

The final product will be a complete IoT-based ICU patient monitoring demonstration ecosystem.

A PC will simulate the bedside ICU patient monitoring device and generate patient vital readings.

A Raspberry Pi will operate as the IoT gateway, collecting and processing incoming information before securely transmitting it to AWS Cloud.

AWS will receive, validate, process, and store the patient monitoring information.

The Doctor Web Application will provide a centralized interface for real-time patient monitoring, historical visualization, device connectivity tracking, and automated alert management.

The system will demonstrate how IoT and cloud computing can be combined to build an intelligent, connected, and offline-resilient patient monitoring architecture.

**Ultimate Goal:**

To develop a fully functional, modular, secure, and presentation-ready IoT-based ICU Patient Monitoring System that demonstrates the complete integration of simulated patient monitoring, Raspberry Pi hardware, AWS Cloud infrastructure, real-time data visualization, and automated alert generation.
